# Ревью плана (Критик) + решения Руководителя и пользователя — 2026-10-20

Вердикт Критика: вернуть на доработку. Все пункты ниже ПРИНЯТЫ Руководителем — внести в plan.md.

## Решения пользователя
- **Вывод из разметки:** уверенное (состояние в блоке степени; эффект заклинания на выбранные цели) — исполняется по режиму, как ручное
  правило; сомнительное (на себя или на цель — неясно; self-effect у action/feat) — кнопка ГМу «Применить (распознано)» прямо в блоке чата
  (не во вкладке — на тысячи предметов вкладка не масштабируется).
- **Макросы (как OnUse в MIDI) — в v1 сразу:** правило может ссылаться на Macro по UUID; исполняется у активного ГМа на фазах
  (использование, после испытаний/по степени, вход/выход зоны, реакция); аргументы — контекст (actor, item, targets, message, degree…).
  Учесть права (`MACRO_SCRIPT`), ошибки макроса не ломают конвейер.

## Дефекты (по важности)
1. **Вывод из разметки (§1.3):** разбирать блоки степеней `<strong>Critical Success/Success/Failure/Critical Failure</strong>` (и русские
   метки после Babele — проверить, по какой разметке; лучше по английскому оригиналу/структуре) с `@UUID[conditionitems…]{Испуган 2}` →
   `byDegree` (значение из подписи ссылки); ссылки на эффекты у заклинаний → `to:"target"` при `targets:selected`; self-effect у action/feat —
   `confidence: low`; low → кнопка ГМу в блоке чата.
2. **Два ГМа (§5, util.queue):** все мутации — `socket.executeAsUser(game.users.activeGM.id, …)`, обработчики отклоняют `!isActiveGM`;
   очередь одного клиента — настоящий сериализатор.
3. **pf2e-automations (§1.6(3), §4, §2 compat):** их Frightful Presence срабатывает по `triggerType:"saving-throw"` на НАШ бросок, т.к. мы
   передаём `item` → при `yield:false` двойной frightened. Брага (`use`) — гонка «проверил-создал». `source[]` — UUID компендиума, не slug
   (`rules/config.json:19060–19063`) → индексировать и по UUID против `_stats.compendiumSource`. Во вкладке при `yield:false` и активной группе —
   предупреждение «двойное применение, отключите группу в pf2e-automations». Не обещать дедуп в харнессе §9-7.
4. **Давность (§2 resumePending, §3.B-8 reconcileZones):** дозапускать только сообщения моложе N минут (настройка) или явно «ждёт ГМа»;
   уважать `modeOf` (не создавать поведения зон в режиме button).
5. **Переставленный шаблон (§3.C-3):** последний регион сообщения задаёт набор целей; неприменённые результаты целей вне него отбрасываются.
   Удаление региона Toolbelt'ом после Target само цели не сбрасывает.
6. **Toolbelt (§3.F):** у ГМа в `createChatMessage` принимать любое `context.type:"saving-throw"` с тем же origin-предметом от актёра из
   целей как результат (покрывает Toolbelt, инлайн `@Check` в карточке, нашу кнопку); разбор `saveVariants` не нужен. Когда Toolbelt ведёт
   испытания — целями считать его цели (`getMessageTargets`).
7. **Расходник с областью (§3.A-2/B-1):** consume-сообщение без `@Template` (`pf2e:51063–51081`) → «регион из карточки = акт использования
   (зона и испытание)»; consume-снимок с `targets:"area"` не считать ожидающим.
8. **Параллельность (§8):** `settings.mjs` и `compat.mjs` (с готовым `automationsCovers`) — в K0; в K0 заглушки с полными сигнатурами и
   именами всех сокет-обработчиков; `socket` экспортировать из `util.mjs` (без цикла с main); живые критерии K1/K3/K5 — через `api.*`
   (attachZone, runChallenge), полные цепочки — K7; K7 разрешены точечные правки чужих файлов.
9. **Схема (§1.1):** явно записать отложенное в v2 (начало/конец хода, «при попадании», начало хода в зоне — либо включить, если дёшево),
   зарезервировать `onTurn`/`zone.events`; «состояние на N раундов» — через обёртку-эффект; ключ каталога — `compendiumSource` поверх slug
   (у NPC один slug ≠ один эффект).
10. **Синхронный резолв (§1.3/§1.5):** slug состояния по uuid — `game.pf2e.ConditionManager.conditions.get(uuid)?.slug`
    (`pf2e:48889–48891`); шаг 4 каскада (`fromUuidSync(sourceId)?.system?.slug`) ненадёжен — индекс без slug.
11. **Перебросы (§10-10):** переброс удаляет старое сообщение и создаёт новое `isReroll` (`pf2e:19670–19679`); маркер `msgId:tokenKey` класть в
    roll options броска; переброс принимать, пока не применено; после применения — «результат изменён» ГМу.
12. **Реакции (§3.D'):** вне боя `reactionSpent` не должен «навсегда» совпадать; активен `pf2e-auto-action-tracker` → по «Использовать»
    отправлять карточку черты (`item.toMessage()`), свой флаг — только фильтр подсказок в текущем раунде боя; не дублировать подсказку на переброс атаки.
13. **Противоречия контракта:** описать `dc:{expr:"markup"}` в схеме; `state.zone.status:"pending"` в перечислении §1.4; `state.yielded` — одно
    решение (и снимок при уступке); дедуп эффекта — одна формула; `expiresAt/roundsLeft` — один источник (поведение).
14. **Зона (§2 zone):** `static events = {tokenEnter, tokenExit}` вместо редактируемого `_createEventsField`; скрытый регион не шлёт событий
    (`region.mjs:2555, :2569`) — свип учитывает `hidden`; `expireZones` на частом `updateWorldTime` — защита от двойного `region.delete()`.
15. **Хуки для pf2e-vision:** вызывать из `createItem`/`deleteItem` нашего состояния с `meta.key` `zone:` (реплицируется, ровно один раз).
16. **Прототипы:** при `ready` предупреждать, если активен любой `pf2e-autoflow-proto-*`; пункт в README.
